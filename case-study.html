Vulnerable Web Application Security Lab

I built a deliberately vulnerable Flask and SQLite web app so I could test common web security problems in a project I controlled. The goal was not only to find bugs, but also to see what those attacks look like from the application and monitoring side.

01

A real app to test

The lab uses Flask for the web app and SQLite for the database. It has login, registration, search, profiles and admin-related pages, so there are real requests and database actions to test.

02

Attack and evidence

I used Burp Suite to look at requests, Hydra to test the login, and SQLMap to test the search point. Each test was tied back to what the app was doing instead of just showing a tool result.

03

Vulnerable and secure modes

The project also lets me compare unsafe behaviour with safer code. This made it easier to see what changed when input checks, parameterized queries, session checks and access rules were added.

04

Made for my own lab

Everything was built as a controlled project for learning and testing. That gave me a safe place to repeat the same attack, change the code and test it again.

02 / 06

What I wanted to learn.

I kept the goals simple: build the app, test it like an attacker, then understand how to make it safer.

01

Build a working vulnerable app

Create the login, registration, search, profile and admin flow first. The security problems should exist inside a working application, not in isolated examples.

02

Test common web problems

Practice SQL injection, broken access control, weak authentication checks and admin access issues using tools I already use in my labs.

03

Understand the request path

Follow a request from the browser to the Flask route and then to SQLite. This helped me understand why a small coding mistake can become a security issue.

04

Connect testing with detection

Keep useful events so the same attack can later be seen by the Mini-SOC dashboard. I wanted the offensive and defensive parts of the project to connect.

05

Test the fixes

After changing the vulnerable code, run the same kind of test again and check whether the old behaviour is still possible.

How the lab works.

The setup is small on purpose. I wanted to understand every part instead of hiding the important steps behind a large framework.

Browser / TesterNormal requests or attack traffic
Flask RoutesLogin, search, profile and admin logic
SQLiteUser and application data

1. Browser to Flask

I first used the application normally and then sent the same requests through Burp Suite. This made it easy to compare normal input with changed parameters.

2. Flask to SQLite

The vulnerable routes show how user input reaches the database. The secure version uses safer query handling instead of joining raw input into SQL.

3. Events for monitoring

Security-related actions can also create events. These events are useful later for the Mini-SOC part of the project, where they become alerts and response actions.

06 / 06

What building the lab taught me.

The biggest part for me was understanding the full path from a request to a bug, and then from a bug to a fix.

Small code changes matter

A small change in how a query or user ID is handled can completely change the security of a route.

Tools are not the whole test

Burp Suite, SQLMap and Hydra helped me test the app, but I still had to understand the request and explain why the result mattered.

Access checks belong on the server

Hiding a button is not access control. The server must check the user and the requested object before returning protected data.

Testing should lead to a fix

I learned more when I repeated the same test after fixing the code. It showed me whether the change actually solved the problem.

Offense and defense can connect

The lab became more useful when the same actions could create events for the Mini-SOC. That gave the project a clear attack-to-detection flow.

Building the lab made the concepts clearer

Instead of only reading about vulnerabilities, I could create them, test them, break the request, fix the code and test again.
